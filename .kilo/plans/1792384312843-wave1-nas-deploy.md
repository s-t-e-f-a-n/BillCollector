## Ordered stages (each ends in an explicit user gate)

   `git log --oneline origin/dev..HEAD` empty (tip `b838201`).
2. NAS baseline (ssh `root@192.168.1.99`):
   - `cd /srv/disk-by-label/Docker/docker-recipes/BillCollector && git log -1`
     → record the **currently deployed commit** (this is the rollback anchor).
   - `docker ps` → record running BillCollector container(s): name, full
     command, port mappings, volume mounts (needed to start the daemon
     consistently in Stage 4).
   - `crontab -l` → record the legacy BillCollector cron entry verbatim
     (needed to restore it in Stage 5 if rollback).
3. Anchor the current state: create an annotated tag on the recorded commit,
   e.g. `git tag -a nas-20261019-<shortsha> <sha> -m "NAS deploy anchor before
   Wave 1"`, verify the object exists locally (`git cat-file -e <sha>^{commit}`
   — it was once pushed to `dev`, so it is in history), and push it to Gitea
   only: `git push origin <tag>`. **Never pass this tag to `sync_github.sh`.**

### Stage 1 — Pre-promotion validation (user runs; gate = exit 0)

Test `dev` at `b838201` — the exact content being promoted.

1. Full regression from the repo root:
   `apps/.venv/bin/python tests/run_regression.py --ini tests/bc_regression.ini`
   → expect **exit 0**. (Exit codes: 1 expectation deviated, 2 mock portal
   failed to start, 3 a real run holds `apps/.bc.lock` → stop the run first,
   4 `--vault` preflight failed.)
2. Docker/NiceGUI-touching changes are in scope (Dockerfile + UI in the 137
   commits) → local image rebuild + smoke:
   - `SKIP_MOUNT_SETUP=1 bash install_docker-image.sh`
   - `docker run --rm -e BC_UI_HOST=0.0.0.0 \
     -v "$PWD/apps/.env:/apps/.env:ro" -p 8766:8000 -p 6080-6095:6080-6095
     billcollector:latest python3 -m billcollector serve` → expect the process
     to stay up and `http://<host-lan-ip>:8766/_alive` to answer 200 (login
     page reachable); then stop the container.
   - Container semantics (learned 2026-10-19 on the NAS): the daemon binds
     `127.0.0.1` inside the container by default, so `BC_UI_HOST=0.0.0.0`
     (env flag or the mounted `.env`) is mandatory for any off-host access;
     the noVNC live view builds its iframe URL from
     `window.location.hostname` + websockify port, so the websockify range
     `6080-6095` (default display_count 16) must be published. The x11vnc RFB
     ports (5999-6014) stay `-localhost` and are never published. From a LAN
     client the URL is the host's LAN IP + published port, not `127.0.0.1`.
     noVNC is unauthenticated on the wire unless `vnc_password` is set in
     Settings (default empty).
3. **Gate:** full regression exit 0 (+ smoke OK). Anything else → fix on
   `dev` (a new dev-commits cycle), re-test; never patch on `main`.

**Log (2026-10-19, first NAS smoke build):** build at `Dockerfile:54`
(`pip check`) failed: `oslo-utils 7.1.0` and `oslo-serialization 5.4.0`
require `tzdata`, which is not installed. Root cause: apt `novnc` →
`python3-novnc` → `python3-oslo.config` → the oslo stack; the noble oslo DEB
metadata declares `Requires-Dist: tzdata` without installing `python3-tzdata`.
Deterministic for every builder of the image. Fix: pin `tzdata==2026.5` in
`apps/requirements.txt` (dev commit, then re-run the NAS build).

**Log (2026-10-19, NAS smoke run):** after the fix, the image built and the
UI answered from the LAN at `http://192.168.1.99:8766` (process stays up,
login page reachable). Two container-side adjustments were required:
`BC_UI_HOST=0.0.0.0` (default bind is container-local `127.0.0.1`) and
publishing the websockify range — the first smoke container mapped only
`8766:8000`, so the noVNC tab (`:6080`) was unreachable from the LAN.
Retest the noVNC tab with `-p 6080-6095:6080-6095` (it is only live while a
run owns a display).

**Log (2026-10-19, ntfy deep link):** the pause push carried the default
`http://127.0.0.1:8000` deep link, unreachable from the LAN. By design:
`ui_base_url` is a Settings-table value (no env layer, `db.get_setting` →
`DEFAULT_SETTINGS` only), and the container cannot know its LAN address or
published port. Set it per deployment in Settings (smoke:
`http://192.168.1.99:8766`; production: the published UI port).

### Stage 4 — NAS deploy (user decides)

1. Root `.env` (local file — no commit): `GIT_BRANCH=dev` → `GIT_BRANCH=main`.
2. `./deploy_remote.sh` → ssh to the NAS, fetch + reset `REMOTE_PATH` to
   `origin/main`, run `install_docker-image.sh` (layer-cache build: a code-only
   deploy re-runs only the final `COPY` + `chown`; the first non-root build on
   the NAS also runs the pip/playwright layers), symlinks + `chown` the mount
   targets, prints the new `git log -1`.
3. Verify deploy: the printed remote commit equals the Gitea `main` tip
   (`b838201`).
4. **Start the daemon** on the NAS (operator action, adapting the container
   convention recorded in Stage 0): `docker run -d` the image with
   `python3 -m billcollector serve`, `apps/.env` mounted read-only at
   `/apps/.env` (it must set `BC_UI_HOST=0.0.0.0` — the daemon's default
   bind is `127.0.0.1`, invisible from the LAN), the same volume mounts as
   before (`Downloads`, `db`, plus `data/`/`browser/profiles` if the existing
   container uses them), UI port 8000 + the websockify range `6080-6095`
   exposed (the noVNC iframe URL = `window.location.hostname` + websockify
   port; x11vnc RFB ports stay container-local).
5. Confirm the daemon healthy: UI login page answers (port 8000), `/_alive`
   200, log shows the scheduler started. The **one-time INI import** happens
   on this first start — the task list must be non-empty (imported tasks
   disabled).
6. **Stop the legacy cron now** (per the confirmed decision): disable the
   recorded cron entry on the NAS.
7. First run: open the UI → Settings: set the UI password, set
   `ui_base_url` to the LAN URL with the **published** UI port (e.g.
   `http://192.168.1.99:8000`) — the ntfy pause deep link
   `<ui_base_url>/runs/<run_id>` must resolve from the phone, so the
   container default `http://127.0.0.1:8000` is wrong for the LAN — and set
   `vnc_password` if the published 6080-6095 range should be authenticated
   → confirm the imported tasks → enable one task.
8. Verify a production run: "run now" (or the next scheduled fire) → the run
   reaches `success` → `Run` + `Download` rows in the DB → the file lands in
   `CONSUMER_DIR` (the paperless consumer folder).
9. If ntfy is configured: a push on run start / pause is expected (skip if not
   set).

### Stage 5 — Rollback (only if Stage 4 fails; user decides)

1. Stop the daemon container; **restore the legacy cron** (the entry recorded
   in Stage 0.2).
2. Root `.env`: `GIT_BRANCH=<anchor tag from Stage 0>`; `./deploy_remote.sh`
   (the `v*`/tag case fetches tags).
3. Verify: remote commit equals the anchor commit; a legacy production run
   succeeds.
4. Rollback never touches Gitea/GitHub branches; the anchor tag is kept. To
   also remove bad code from Gitea `main`: revert on `dev` → Stage 1 →
   Stage 2 (a normal cycle), never an edit on `main`.

## Risks / failure modes

- **Stage 2 ff-only fails** → `main` diverged (direct commit or non-ff
  external push): stop and report; never force.
- **`sync_github.sh` killed mid-run** → `git worktree prune` cleans the leak;
  re-runs are idempotent.
- **Coverage gap (accepted):** the cron stops as soon as the daemon is
  healthy, before the first task is enabled/verified — no collections happen
  in that window. The user accepted this over keeping the cron running.
- **NAS build surprises:** first non-root build on the NAS runs the full
  pip/playwright layers; the `chown` of `CONSUMER_DIR`/`DB_DIR` to UID/GID
  1000 must be allowed by the NAS share permissions or the deploy aborts
  before any run (by design).
- **Anchor commit unreachable locally** (if the NAS runs an old `dev` tip
  that was later rewritten): verify in Stage 0.3 before tagging; if absent,
  the anchor falls back to the last release tag `v0.4` (Gitea hash `50354d2`)
  — note that also reverts the Docker changes (pre-non-root image).
- **Local tags are untrustworthy** (mixed lineage) — all tag work in this
  plan refers to Gitea/GitHub refs, checked with `git ls-remote`.
