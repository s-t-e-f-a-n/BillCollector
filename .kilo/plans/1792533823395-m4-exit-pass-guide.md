# M4 Exit Pass Guide

Plays a **new user** from the README alone: stand up the daemon stack from a
fresh clone, set the password, walk the onboarding wizard, and collect one
document from the browser — no shell access to the daemon. It is the M4 goal
check: a new user can go from a clone to a collected document using only the
docs and a browser.

**Status:** user-gated. Needs a Docker host with a running Vaultwarden +
`bw serve`. The browser half (set password, wizard, Run now, view Downloads)
is driven by a human; the Docker-side prep can be done by the agent over ssh.

Two halves:

- **Half A — Mock portal (primary, self-contained).** No real portals. Uses
  the repo's `tests/mock_portal` on the Docker host. This is the repeatable
  acceptance check.
- **Half B — Real Vaultwarden + real portal.** The production new-user path,
  executable from the README Quick Start alone. Run it when you want to
  validate against the real stack (the mock half stands in for it).

An optional third piece (ntfy + pause drill) exercises the pause-and-step-in
flow.

---

## Prerequisites

- **A Docker host.** Any of: the NAS, a VM, Docker Desktop. It is the machine
  where `docker compose up` runs. Call it `<host>`.
- **Vaultwarden + `bw serve`** already running in their own compose stack
  (prerequisite, not part of this stack). Reachable from `<host>`. The daemon
  fetches every task's login from the vault, so this is required for a run to
  reach `success` — "skip the vault" in the wizard only works if you are not
  going to run a task to completion.
- **A browser** on a machine that can reach `<host>`'s published UI port
  (default `8766`) over the LAN.
- **Half A only:** the repo's `tests/mock_portal` must be runnable on
  `<host>` (needs `fastapi` + `uvicorn`; use the repo's `apps/.venv` or a
  throwaway venv).

> The container reaches host-local services (the mock portal, Vaultwarden,
> `bw serve`) via `host.docker.internal` (compose sets
> `extra_hosts: host.docker.internal:host-gateway`). Any URL the **container**
> must open (the recipe goto, the wizard's vault Check) therefore uses
> `http://host.docker.internal:<port>` when the target runs on `<host>` — not
> `127.0.0.1`.

## Half A — Mock portal (primary)

### A0. Docker-side prep (on `<host>`)

1. Fresh clone (or a clean checkout of `dev`):
   ```bash
   git clone <repo> billcollector-exitpass && cd billcollector-exitpass
   git checkout dev
   ```
2. Create the data folders the container user writes to **before** the first
   `up` (Docker would create a missing bind-mount folder root-owned, and the
   container could not write into it):
   ```bash
   mkdir -p apps/Downloads apps/db apps/data apps/browser/profiles
   sudo chown -R 1000:1000 apps/Downloads apps/db apps/data apps/browser
   ```
3. Create the app config (a missing `apps/.env` makes Docker create a
   *directory*, which breaks the read-only mount):
   ```bash
   cp apps/.env.example apps/.env
   ```
   Set `BW_API_URL` to the HTTP URL of your local `bw serve` API. From the
   container's point of view that is usually
   `http://host.docker.internal:8087` (the `bw serve` port on `<host>`).
4. (Optional) Root `.env` for compose variables — all have defaults:
   `BC_UI_PORT` (published UI port, default `8766`), `NTFY_HOST`, `APP_UID` /
   `APP_GID`.
 5. Start the mock portal on `<host>` **bound to all interfaces** (the
    default `127.0.0.1` bind is host-loopback only — a containerized daemon
    reaching it via `host.docker.internal` gets *connection refused*, as do
    the host's LAN name/IP, see Gotchas):
    ```bash
    python3 -m tests.mock_portal --host 0.0.0.0
    # or: apps/.venv/bin/python -m tests.mock_portal --host 0.0.0.0
    ```
    Leave it running for the duration of the pass.
6. Build + start the stack:
   ```bash
   docker compose up -d --build
   ```

**Verify before touching the browser:**
- `docker compose ps` → `billcollector` is `running` (healthy after the
  `start_period`).
- `curl -fsS http://127.0.0.1:8787/health` → the mock portal answers.
- `curl -fsS http://127.0.0.1:<BW_API_URL port>/status` (or the wizard's Check
  later) → `bw serve` is reachable and `unlocked`.

### A1. Seed the mock credentials in the vault

The daemon resolves a task's login from a vault item named
`<service> <user>`. For the recommended task (`testhappy` / `user1`) create an
item whose login matches `tests/scenarios.py` (the source of truth):

- Item name: `testhappy user1`
- Username: `user1`
- Password: `user1-pass`
- TOTP: the **base32 secret** `ITMSBTU3L2H7CAOQWNRNCZIFDY`
  (`TOTP_SECRETS[("happy", "user1")]`). The daemon computes a fresh RFC 6238
  code from the secret at run time, so the secret — not a fixed code — goes in
  the vault item. (The `otp: "123456"` in `CREDENTIALS` is only what the
  non-vault regression harness feeds the engine directly.)
- URI (informational only — the engine visits the recipe's goto URL, not this):
  `http://host.docker.internal:8787/happy/`

Confirm `bw status` (or the wizard's Check) reports `unlocked`.

### A2. Browser walk (the M4 goal — human-driven)

1. Open `http://<host>:8766/`. The first start shows the **set-password**
   form. Set a password. You land on `/onboarding`.
2. **Wizard → Vault:** enter the vault API URL
   (`http://host.docker.internal:8087` if `bw serve` is on `<host>`), press
   **Check** (expect *reachable and unlocked*), then **Save**.
3. **Wizard → Tasks:** the auto-imported real tasks (winSIM, KabelDeutschland,
   …) are listed and **disabled**. Use **New task**:
   - service `testhappy`, user `user1`, cron `0 0 1 * *`, enabled.
   Leave the real tasks disabled (their recipes point at real portals).
4. **Wizard → Finish:** **Finish onboarding** → you land on the Dashboard `/`.
5. **Edit the recipe (mock-half specific):** open the recipe editor for
   `testhappy` (`/recipes/testhappy`) and change the goto URL from
   `http://127.0.0.1:8787/happy/` to **`http://host.docker.internal:8787/happy/`**
   (the container's browser must reach the host's mock portal via
   host-gateway). Save.
6. **Dashboard:** press **Run now** for the `testhappy` task.
7. Watch the run (Session page; the noVNC tab shows the live browser) until it
   reaches `success`.
8. **Downloads** page: the collected document is listed. Confirm it also landed
   in the consumer folder on `<host>` (`apps/Downloads` bind mount).

### A3. Pass criteria (checklist)

- [ ] `docker compose up -d --build` succeeds; container healthy.
- [ ] Set-password form → wizard reachable.
- [ ] Wizard vault Check green (or deliberately skipped + flagged).
- [ ] New task `testhappy`/`user1` created and enabled.
- [ ] Recipe goto URL = `http://host.docker.internal:8787/happy/`.
- [ ] Run now → run reaches `success`.
- [ ] Document visible on the Downloads page **and** in the consumer folder.
- [ ] No shell access to the daemon was needed for any step.

## Half B — Real Vaultwarden + real portal

The production new-user path; executable from the README Quick Start alone
(clone → folders → `apps/.env` → `docker compose up -d --build` → set password
→ wizard → first task). Differences from Half A:

- `apps/.env` `BW_API_URL` = the real `bw serve` API URL.
- No mock portal. The wizard's vault Check goes green against the real vault.
- Enable a real task whose recipe + vault item point at a real portal you are
  allowed to run against.
- Recipe goto URL is the real portal (no `host.docker.internal` edit unless
  the portal runs on `<host>`).

Use it to confirm the docs carry a real user through, not just the mock stand-in.

## Optional: ntfy + pause drill

Exercises pause-and-step-in with a real phone push.

1. Add `NTFY_HOST=http://ntfy` (optional `NTFY_BASE_URL=http://<host>:2086`) to
   the root `.env`; start with `docker compose --profile ntfy up -d`.
2. New task `testwaituser` / `user1` (service `testwaituser`, user `user1`),
   seed its vault item, and edit its recipe goto URL to
   `http://host.docker.internal:8787/waituser/`.
3. Set the ntfy topic in Settings; subscribe from your phone.
4. **Run now** → the run pauses at the `wait_user` step (task shows
   `waiting`) → you get an ntfy push with a deep link → open it → the Copilot
   view (screenshot + numbered elements + Resume/Cancel) → **Resume**.

## Cleanup

- `docker compose down` (add `--volumes` to drop the ntfy cache).
- Stop the mock portal.
- Remove the throwaway clone if it was disposable.
- **Do not** touch the production deployment (separate directory/branch on the
  NAS) — this pass runs in its own fresh clone.

## Gotchas (verified 2026-10-21)

- **The bundled ntfy image is `binwiederhier/ntfy`** (caught in the ntfy +
  pause drill, 2026-10-21). The compose file pointed at `ntfy.sh/ntfy`, and a
  first fix pointed at `ntfy/ntfy`; **neither repository exists on Docker Hub**
  — the pulls fail with a registry 404 / `pull access denied`. The official
  image is `binwiederhier/ntfy` (Docker Hub, published by the ntfy author), and
  it ships **no default command** — the compose service must pass
  `serve --cache-file /var/cache/ntfy/cache.db` explicitly (per the official
  install docs), or the container exits immediately. Fixed on dev — pull before
  running the drill.

- **The mock portal must run with `--host 0.0.0.0` under Docker** (caught in
  the mock half, 2026-10-21). The `tests.mock_portal` CLI binds
  `127.0.0.1` by default — host-loopback only. A containerized daemon reaching
  it gets *connection refused* via **every** host-routable name:
  `host.docker.internal` (the host-gateway/bridge IP), the host's LAN name
  (e.g. `solg.fritz.box`), and even the host's LAN IP, because none of those
  interfaces is the host's loopback. The recipe's goto URL
  (`http://host.docker.internal:8787/...`) is correct — the portal just has to
  listen on all interfaces. The CLI gained `--host` on dev for this; pull
  before the pass.

- **The onboarding gate once 307'd NiceGUI's own static assets** (caught in
  A1, 2026-10-21). While onboarding was active, an authenticated browser's
  module imports (`/_nicegui/<ver>/static/*.mjs`) were redirected to
  `/onboarding`, the JS bundle died, and the page rendered the dead
  "Your browser does not support ES modules" fallback (`#esm-fallback` in
  NiceGUI's `index.html`). The gate now exempts public paths
  (`is_public_path`), so static files, `/_alive`, and the socket mount pass
  through. Fixed on dev — rebuild the stack after pulling.

- **The daemon always fetches credentials via the vault.** A task cannot
  reach `success` without a resolvable vault item. "Skip the vault" in the
  wizard is only viable for a no-run wizard walkthrough.
- **The recipe goto URL is literal**, not templated: `process_argument`
  substitutes only exact `{{...}}` placeholders (`{{USERNAME}}`,
  `{{PASSWORD}}`, `{{OTP}}`). A containerized daemon reaching a host-local
  mock portal therefore needs the goto URL rewritten to
  `http://host.docker.internal:8787/<site>/`.
- **Missing `apps/.env` → Docker creates a directory** at the mount point,
  breaking the read-only mount. `cp apps/.env.example apps/.env` is mandatory.
- **Missing bind-mount folders are created root-owned** → the container
  (UID 1000) cannot write. Create + chown the data folders before the first
  `up`.
- **The mock service is not auto-imported.** `bc_default.ini` / `bc_test.ini`
  hold only the real services, so `testhappy` must be created via the wizard's
  **New task** (or an **Import from INI** of a scope INI that lists it).
- **The vault item's URI is informational** — the engine visits the recipe's
  goto URL, not the vault URI. Keep the two consistent to avoid confusion.
