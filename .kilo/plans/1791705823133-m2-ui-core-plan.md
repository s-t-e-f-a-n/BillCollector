# BillCollector — M2: UI core (execution plan)

Master plan: `.kilo/plans/1790364274061-billcollector-nicegui-daemon-plan.md` (v3,
M2 section). Dashboard spec: `.kilo/plans/1790468502492-gui-concept-dashboard-spec.md`
(the dashboard line in v3 is superseded by it). M1 is complete and committed to `dev`
(C7.6 exit validation done 2026-10-11; full unit suite 155/155 green).

**Goal:** the full task lifecycle is operable from the web UI against the mock portal —
login, dashboard, task management, run now/stop with live log, task detail with history
and step screenshots, recipe editing with validation + git commit, downloads, settings.
Session *view* (Copilot + noVNC) and the recipe repair flow stay in M3; in M2 the UI
surfaces pauses read-only (badge, prompt, deadline, pause screenshot) — resolution is
still via the control socket (as in M1).

## Verified current state (dev, 2026-10-11)

- `apps/billcollector/`: `cli.py` (`serve`/`run`), `ui/app.py` (skeleton: `/_alive`,
  index page, `build_lifecycle` startup/shutdown wired to `ui.run`), `db.py` (Task/Run/
  PageStatus/Download/Settings, `import_ini` on first serve start), `scheduler.py`
  (`sync_task(task_id)` is the task-change hook, `resync()` startup), `orchestrator.py`
  (`start_run(task_id)` = run callback, `run_log_path(run_id)`, `Run.log_path` recorded
  by the monitor), `runner.py`, `pause.py`, `control.py` (`ControlClient` for tests),
  `display.py`, `notify.py` (ntfy deep link `<ui_base_url>/runs/<run_id>`), `downloads.py`,
  `vault.py`, `pagestate.py`, `interrupt.py`, `config.py` (`DEFAULT_SETTINGS`, `BC_*` env
  redirects).
- DB schema: **no** `Task.profile_reset_at` yet (the dashboard spec's DDL has it; the
  current schema does not). No migration framework — schema is `CREATE TABLE IF NOT
  EXISTS` only; M2 adds a small additive column-migration helper.
- `apps/bc_ui.py`: fast-track standalone UI for the legacy batch entry point; port 8000;
  `.bc_ui_run.json` state file (covered by `.gitignore`).
- Tests: 155 unit tests, stdlib `unittest`, run `python -m unittest discover -s tests`
  from the repo root. **pytest is NOT installed** in `apps/.venv`; `nicegui.testing`
  ships with nicegui 3.17.1 (needs pytest to run). `tests/__init__.py` exists; tests add
  `apps/` to `sys.path` themselves.
- Mock portal (`tests/mock_portal/`, port 8787) + Layer A/B sites + `tests/scenarios.py`;
  Layer B vault items exist. Dev host has the full Xvfb/x11vnc/websockify/novnc stack.
- Legacy `helpers/BillCollectorCheckRecipe.py`: `CheckRecipe(recipe_file, schema_file)`
  returns the recipe dict or None — but on some failure paths it calls builtin
  `exit(1)` (SystemExit) and reports validation errors only via `logger`, so it is not
  a clean UI API. It is import-safe (no Playwright: `helpers` pulls only
  `BillCollectorHelpers` + `sshkeyboard`), and the runner already uses it.
- Recipes: per-service YAML (`recipe-pw__<service>.yaml`), shape `services[].steps[]`
  with `step`, `description`, optional `graceful`, `methods[]`, nested `steps[]` under
  `expect_download`; `$schema` line points at `recipe-pw-schema.yaml`.
- `ui.editor` (CodeMirror), `ui.table`, `ui.log`, `ui.timer` are available in
  nicegui 3.17.1.

## Locked decisions

1. **Auth (v3 decision 5, confirmed):** session-cookie login, bcrypt hash in
   `Settings.ui_password_hash`; `BC_UI_PASSWORD` from `.env` seeds the hash on first
   start when set. **First start with neither:** the login page shows a one-time
   *set-password* form (user-confirmed 2026-10-11); afterwards it is the normal login
   form. Password changeable in the Settings page. Single operator, no multi-tenancy.
2. **Middleware:** app-level Starlette `SessionMiddleware` (secret persisted in the
   `Settings` table as `session_secret`, generated on first start so sessions survive
   daemon restarts) redirects unauthenticated requests to `/login`; public paths:
   `/login`, `/_alive`, and NiceGUI static `/_*`. Protected page functions additionally
   check the session defensively (page builders run server-side per navigation).
3. **Test stack (v3 validation line, user-confirmed 2026-10-11):** `pytest` as a
   **dev-only** dependency (`apps/requirements-dev.txt`, never in the runtime
   `requirements.txt`); `nicegui.testing` `User` (no browser) for page-logic tests and
   `Screen` (real Chromium) where layout matters. Existing `unittest` files are
   collected by pytest unchanged. Suite command becomes
   `apps/.venv/bin/python -m pytest tests/ -q` from the repo root. M2 exit E2E on the
   mock portal stays a **recorded manual pass** (M1 C7.6 pattern) — the committed suite
   stays fast and display-independent.
4. **`apps/bc_ui.py` is deleted in M2** (user-confirmed): Run now + log pane +
   orchestrator orphan cleanup fully replace it; the legacy batch path stays available
   via `BillCollector.sh`/cron until M4. Its `pages` broadcast pattern is absorbed into
   the orchestrator's log-subscriber API.
5. **Recipe validation core:** new `billcollector/recipes.py` (YAML load + jsonschema
   against `config.RECIPE_SCHEMA`, returns `(ok, error, data)` — no legacy import, no
   `exit()` path) used by the recipe editor and (M3) the repair flow. The legacy
   `BillCollectorCheckRecipe.py` is left unchanged for the batch/CLI path.
6. **Live log:** the orchestrator's monitor pushes each stdout line to registered
   subscriber callbacks (`add_log_subscriber`/`remove_log_subscriber`); pages register
   on connect, unregister on disconnect. A page opening a finished run first loads the
   existing `Run.log_path` file, then follows.
7. **Stop:** new `orchestrator.stop_run(task_id)` — SIGTERM the runner's process group,
   escalate SIGKILL after 10 s (dashboard spec; `bc_ui.py` semantics). The runner's own
   SIGTERM handler finalizes the run `interrupted` (C7.5).
8. **Profile reset:** rejected while the task is `running`/`waiting`; deletes the
   profile dir; records `Task.profile_reset_at` (new column, additive migration via
   `PRAGMA table_info`). Next run cold-starts.
9. **Task creation fields:** service, user, cron (default `0 0 1 * *`), enabled.
   `recipe_file` is derived from the service (read-only in the UI: the recipe is
   shared by all tasks of the service — made explicit). A missing recipe file warns but
   does not block creation (the run would fail pre-recipe-check, task released by the
   orchestrator's no-row path). Every create/enable/cron change calls
   `scheduler.sync_task`. No task deletion in M2 (disabling is the off switch).
10. **Screenshots/static:** `config.RUN_DIR` (`<data>/runs/<run_id>/…`) is registered as
    a NiceGUI static directory named **`runfiles`** (`/runfiles/<run_id>/step_N.png`,
    `pause_N.png`) — deliberately not `/runs`, which is reserved for the ntfy deep-link
    route. The deep link `/runs/<run_id>` (M2: the session view is M3) redirects to the
    task detail page of the run's task.
11. **Pause surfacing in M2 (read-only):** dashboard `waiting` badge + highlighted row;
    task detail shows pause prompt, reason, deadline countdown, and the last pause
    screenshot (from `Run.pause_context` / `pause_<n>.png`). Copilot/noVNC resolution
    is M3.
12. **Settings page fields:** UI password (change), `ntfy_topic`,
    `pause_deadline_seconds`, `max_concurrency` (takes effect on next daemon start —
    the semaphore is built at construction), `git_commit_enabled`, `download_dir`,
    `display_start`, `ui_base_url`, `vnc_password`. All in the `Settings` table.
13. **Git auto-commit (v3 decision 8):** `gitcommit.py` — `git add` + commit of the
    recipe file only, message `recipe(<service>): <summary>`, only when
    `git_commit_enabled`; "nothing to commit" is a success, not an error.
14. **Layout:** shared NiceGUI layout (header + left menu: Dashboard, Downloads,
    Settings; per-task and per-recipe pages under it), login page standalone. English UI
    (v3 decision 17). `serve` binding unchanged (127.0.0.1:8000 default, env override).
15. **ini import:** already implemented (M1: `import_ini` on first `serve` start,
    marker in `Settings`). M2 only exercises it in the E2E pass — no work item.

## Chunks (D1 → D6)

Same pattern as M1's C-chunks: implement in order; each chunk is independently
committable, ends with the **full suite green** (`apps/.venv/bin/python -m pytest tests/
-q`), plus its own verification. A fresh session resumes at the first chunk not yet
committed. Commit style follows the repo convention (`feat:`/`test:`/`doc:` +
`(M2 chunk D<n>)`).

### D2 — App shell + dashboard (read-only)

### D3 — Run actions + task management

- **D3.1 `orchestrator.stop_run(task_id)`:** SIGTERM the task's live runner group,
  wait 10 s, SIGKILL; the runner's own handler finalizes `interrupted` (C7.5) — the
  orchestrator just signals. Returns True/False (no live runner).
- **D3.2 Dashboard actions:** row **Run now** (works for disabled tasks; manual one-off,
  schedule unchanged; disabled while the task is active) and **Stop** (enabled only
  while running); toolbar **Run (filtered)** — enqueues all **enabled** tasks in the
  filtered set via `start_run` (semaphore serializes; skipped tasks are reported in a
  notify). All calls go through `orchestrator.start_run` / `stop_run` (the same
  callbacks the scheduler uses).
- **D3.3 Task management (`ui/tasks.py` or a dialog from the dashboard):** create task
  (service, user, cron default `0 0 1 * *`, enabled toggle; derived `recipe_file` shown
  read-only; warn when the recipe file is missing — D3.9), edit (cron, enabled),
  enable/disable toggle; each change → `db.update_task` + `scheduler.sync_task`.
- **D3.4 Profile reset (logic):** `db.py` — additive migration: `PRAGMA table_info(Task)`
  check → `ALTER TABLE Task ADD COLUMN profile_reset_at TEXT` (once, idempotent);
  `reset_profile(db, task_id)` — reject unless status `idle` (raise/return error),
  `rmtree` the profile dir if present, set `profile_reset_at`, update the task. The UI
  button lands on the task detail (D4).
- **D3.5 Tests:** unit — `stop_run` on a sleeping stub runner → process group gone,
  run ends `interrupted`, task `idle`; no-op when no live runner; profile reset (temp
  profile dir deleted, timestamp set, rejected for a running task); migration idempotent
  (fresh DB + pre-existing DB both end with the column). UI — Run now calls
  `start_run` (stubbed orchestrator; button disabled afterwards until the status
  refreshes), Stop calls `stop_run`, Run (filtered) enqueues exactly the enabled tasks
  in the filter, create form inserts a task (stubbed scheduler: `sync_task` called),
  enable toggle flips the row.
- **Baseline:** from the UI: start/stop runs, create/enable/schedule tasks, reset a
  profile; full suite green.
- **Verify (manual):** scratch env + mock portal: create `testhappy`/`user1` via the UI,
  enable, Run now → success; Stop mid-run → `interrupted`; reset profile → dir gone,
  next run shows the consent banner again (warm-profile proof, M1 pattern).

### D5 — Recipe editor + git auto-commit

- **D5.1 `recipes.py`:** `load_recipe(path) -> (ok, error, text, data)`;
  `validate_recipe(text, schema_path) -> (ok, error, data)` (yaml.safe_load +
  jsonschema against `config.RECIPE_SCHEMA`; structured error text, never raises);
  `parse_steps(data) -> list` (the step tree: step number, description, graceful,
  methods with arguments, nested steps under `expect_download` — drives the step-tree
  sidebar); `save_recipe(path, text)` (atomic: temp file in the same dir + replace;
  refuses to save unvalidated text — the UI always validates first).
- **D5.2 `gitcommit.py`:** `git_commit(paths, message) -> (ok, output)` —
  `git -C <repo> add <paths>` + `git commit -m <message>` (subprocess, captured);
  "nothing to commit" → (True, …); non-zero → (False, output tail). Repo root
  resolved from `config.APP_DIR` (parents). The UI only calls it when
  `git_commit_enabled`.
- **D5.3 `ui/recipes.py`:** `/recipes/<service>` — YAML editor (`ui.editor`, loads the
  current file; the per-service file is shared by all tasks of the service — shown
  explicitly with the list of that service's tasks); **step tree** sidebar (read-only,
  from `parse_steps`, re-parsed on edit, marks steps that fail YAML parse); **Validate**
  button (inline result, auto on save); **Save** = validate → `save_recipe` →
  `git_commit([file], "recipe(<service>): <summary>")` when enabled (summary: first
  changed service description or "edited via UI"); after a successful save: per-task
  **Run now** buttons (the D3 action, one click away).
- **D5.4 Tests:** unit — `validate_recipe` (valid, invalid-locator, broken YAML,
  missing file), `parse_steps` (nested `expect_download` steps, graceful flag),
  `save_recipe` atomicity (file replaced, no partial on failure), `git_commit` in a
  **real temp git repo** (commit lands with the exact message; second no-op commit →
  ok without a new commit; dirty-unrelated-file scenario: only the recipe file is
  committed). UI — editor loads the current YAML; invalid edit → error shown, file on
  disk unchanged; valid edit → file written (+ commit in the temp repo when the toggle
  is on).
- **Baseline:** recipe edit → save → validation → git commit works end-to-end in the
  UI; full suite green.
- **Verify (manual):** on the mock-portal task: edit `recipe-pw__testhappy.yaml`
  (e.g. step 2's description), Save with `git_commit_enabled` → `git log` shows
  `recipe(testhappy): …`, `git diff` clean; with the toggle off → file written, no

## Risks

- **nicegui.testing on this host:** `Screen` tests drive a real Chromium via the repo
  browser build (`PLAYWRIGHT_BROWSERS_PATH` in `tests/conftest.py`); `User` tests need
  no browser. If `Screen` proves flaky, page-logic tests stay on `User` and the manual
  E2E pass (D6.4) is the browser proof — the committed suite must not depend on a
  display.
- **APScheduler next-run display:** `next_run` is read from the live jobstore
  (`trigger.next_fire_time`), not the Task table — after a daemon restart the jobs are
  resynced from the Task table, so the display stays correct; a disabled task has no
  job → `—`.
- **Static dir vs deep link:** `/runfiles` vs `/runs/<id>` are deliberately distinct
  (D2.3/D4.2) — keep the naming when adding M3 routes.
- **SQLite writers:** UI writes (Task/Settings) are short single-row writes; the WAL +
  busy_timeout regime from M1 is unchanged.
- **git commit in the UI:** the repo is a bind mount on the NAS, single operator →
  conflicts unlikely; only the recipe file is staged (never `git add -A`); the toggle is
  off by default.
- **Session secret persistence:** the `Settings` row must be written **before** the
  first request is served (startup), otherwise sessions die on every restart.
- **`bc_ui.py` removal:** no code path imports it (it is a standalone script); verify
  nothing in docs/CI references it before deleting.

## Out of scope (M2)

- Copilot session view, noVNC embedding, recipe repair flow with candidate picker (M3)
- Onboarding wizard, Docker Compose, docs, cron retirement (M4)
- Task deletion, multi-user, e-mail/SMTP, paperless consumer, custom REST API
- Any change to the runner/pause/control-socket protocol (M1 contract stays; M3 reuses it)
- `playwright codegen` in the UI
