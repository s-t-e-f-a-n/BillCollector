# BillCollector wiki brief## PurposeThis wiki is the durable context layer for coding agents working in thisrepository (primary audience) and human maintainers (secondary). It lets anagent orient in minutes instead of re-deriving the architecture on every task.The code is the single source of truth; the wiki is a derived index ofsource-grounded claims. When a page and the code disagree, the code wins andthe page is fixed in the same task.## Scope and prioritiesDocument, in this order:1. Architecture overview - the two coexisting operating modes:   (a) the cron/batch engine (apps/BillCollector.py ->   apps/BillCollectorServices_pw.py, headless Chromium via Playwright, SQLite   step recording, exit-code semantics) and (b) the NiceGUI daemon   (apps/billcollector/: cli, scheduler, orchestrator, runner, pause/repair,   control, ui/* pages). Include a valid Mermaid diagram of both modes and   their shared pieces.2. Shared interfaces - the four contracts from CONTRIBUTING.md that must not   break without an issue: the SQLite schema (apps/billcollector/db.py),   the daemon control protocol (apps/billcollector/control.py), the recipe   contract (recipe-pw YAML + recipe-pw-schema.yaml under   apps/recipes_playwright), and the process exit codes. For each: shape,   invariants, where it is enforced.3. Recipe system - YAML structure (services/steps/methods), locator and   page-level methods, variables ({{USERNAME}}, {{PASSWORD}}, {{OTP}}),   expect_download, graceful steps, validation via   helpers/BillCollectorCheckRecipe.py, file naming convention.4. Run lifecycle - scheduling (cron and apps/billcollector/scheduler.py),   the flock run lock, per-service failure isolation, step-by-step DB   recording, and pause/resume/recipe-repair of an interactive session.5. Vault transport and security - BW_API_URL vetting, per-attempt DNS checks,   what is refused and why; link doc/vault_transport.md rather than restating   it.6. Web UI - one short section per page (dashboard, tasks, task detail,   recipes, settings, session, log pane, auth): purpose, state, actions.7. Testing and verification - the regression harness (tests/run_regression.py,   tests/mock_portal, tests/scenarios.py), unit tests, and the Docker context   check. For each documented behavior, give the command and the expected   outcome that proves it.8. Development and deployment - install_local.sh, install_docker-image.sh,   deploy_remote.sh, the trunk-based model with release tags, the BuildKit   layer-cache ordering, and the public mirror (Gitea main -> GitHub with   .kilo/.vscode/.private stripped).9. Roadmap - the public-safe state of the daemon migration (what is live,   what is planned), without referencing internal planning documents.## Exclusions (hard rules)- No references to .kilo/ (plans, skills, agents, worktrees): those paths are  stripped from the public mirror, so links to them break on GitHub and plan  paths are forbidden in public sources.- No internal hostnames, URLs, NAS details, personal data, portal screenshots,  or anything that would not survive publication on GitHub.- No duplication of the README quickstart/configuration walkthroughs: link to  README.md sections instead.- No documentation of runtime artifacts (apps/db, apps/browser, Downloads,  logs, .venv).## Page conventions- One concept per page, stable slug; link related pages; keep pages short and  link instead of duplicating.- Ground every factual claim in source evidence (file path, with symbol or  line where stable); prefer code identifiers over prose when naming  behavior.- Each page: purpose, key files, invariants/contracts, verification (command  + expected result), known pitfalls.- Mermaid for architecture and lifecycle; keep fences parseable (the  finalizer degrades unparseable ones).- English only, including comments in any code snippets.## Update policy- Refresh (openwiki --update) when: a milestone lands, a shared interface  changes (schema, control protocol, recipe contract, exit codes), a module or  UI page is added or removed, the Dockerfile or deployment scripts change  behavior, or a release tag is cut.- An agent that changes a documented contract updates the affected wiki pages  in the same task, as a separate "doc: wiki:" commit following the repo  commit style.- The wiki is versioned with the code and reviewed like code; it must never  lag a merged interface change.
